1. INTRODUCTION                                           *lvim-fuzzy-intro*

lvim-fuzzy is the shared fuzzy-matching ENGINE for the lvim-tech set. lvim-cmp
and lvim-picker both rank through it, so they order results one identical way.

The hot path is a small Rust shared library (in `native/`) loaded IN-PROCESS via
LuaJIT FFI: an affine-gap local-alignment scorer with first-char / word-boundary
/ camelCase / consecutive-run bonuses folded into the score, an inter-candidate
AVX2 SIMD tile that ranks 16 candidates per instruction, an O(1) byte-signature
prefilter, and a stable O(n) radix sort. On our benchmark it is faster than a
leading Rust SIMD fuzzy matcher on every tested query, at both 5k and 20k
candidates.

The Lua<->native boundary is COARSE: the candidate set is uploaded ONCE per
completion / pick (|lvim-fuzzy.prepare|), then every keystroke is a SINGLE FFI
call carrying only the query and returning sorted indices + scores — never a
call per candidate.

When the library is not present (no Rust toolchain, or a platform without a
prebuilt binary) lvim-fuzzy transparently uses a BYTE-IDENTICAL pure-Lua matcher
(|lvim-fuzzy-backends|), so results never change depending on the backend.

The ranking model is fixed on purpose: lvim-fuzzy is an engine, not a UI, and
its determinism is a guarantee its consumers rely on. The result order is a
TOTAL, deterministic order: score descending, then shorter candidate, then
source index ascending — no arbitrary equal-score reshuffling.

2. SETUP                                                  *lvim-fuzzy-setup*

Calling setup() is optional; the defaults work. setup() merges your overrides
into the live config in place.
>lua
  require("lvim-fuzzy").setup({
      backend = "auto",         -- "auto" | "native" | "lua"
      library_path = nil,       -- explicit .so path; nil = auto-probe
      max_results = 1000,       -- cap on ranked results per query (0 = no cap)
      warn_on_fallback = true,  -- notify once when the Lua fallback is used
  })
<
                                                         *lvim-fuzzy-config*
backend        "auto" loads the native library when present and ABI-compatible
               and uses the Lua fallback otherwise; "native" requires the .so
               (reported as an error in |:checkhealth|); "lua" forces the
               fallback.
library_path   Absolute path to liblvimfuzzy.{so,dylib,dll}. nil probes, in
               order: `$LVIM_FUZZY_LIB`, `native/build/`, `native/target/release/`.
max_results    Hard cap on the materialised result list per query, so a broad
               query over a huge set never builds hundreds of thousands of rows
               on a keystroke. 0 disables the cap.
warn_on_fallback  Emit one INFO notification the first time a match runs on the
               pure-Lua fallback.

3. API                                                      *lvim-fuzzy-api*

                                                        *lvim-fuzzy.prepare()*
require("lvim-fuzzy").prepare({candidates})            → ctx
    Build a matching context for a fixed candidate set (a list of strings,
    searched by their bytes). Do this ONCE per completion / pick. Returns an
    opaque `ctx` to pass to |lvim-fuzzy.match|.

                                                          *lvim-fuzzy.match()*
require("lvim-fuzzy").match({query}, {ctx})            → results, count
    Rank `ctx`'s candidates against `query`. Returns a list of
    `{ index = <1-based index into candidates>, score = <integer> }` in ranked
    order, and the count. Call it on every keystroke — it is one FFI call.

                                                         *lvim-fuzzy.append()*
require("lvim-fuzzy").append({ctx}, {candidates})     → count
    Append NEW candidates to an existing context, extending it INCREMENTALLY:
    only the new candidates are built (their offsets / signatures / lengths are
    appended in place; the existing pool is never re-scanned). A subsequent
    |lvim-fuzzy.match| ranks the whole grown set, and the result is
    byte-identical to `prepare(old ++ new)`. The cost is proportional to the
    number of NEW candidates, not the pool size (see |lvim-fuzzy-append|).
    Returns the new total count.

                                                           *lvim-fuzzy.free()*
require("lvim-fuzzy").free({ctx})
    Release a context. On the native backend, if `ctx` is the active slot its
    SoA memory is freed eagerly. Optional — not calling it is harmless.

                                                         *lvim-fuzzy.filter()*
require("lvim-fuzzy").filter({candidates}, {query})    → results, count
    One-off stateless rank (prepare + match in a single call) for callers that
    do not keep a context. Does not disturb an active prepared context.

                                                      *lvim-fuzzy.positions()*
require("lvim-fuzzy").positions({candidate}, {query})  → cols|nil
    Matched-char BYTE columns (1-based, ascending) of `query` inside ONE
    candidate — the exact alignment the scorer credits, so highlighted chars
    always agree with the ranking. Intended for a menu's few VISIBLE rows.
    Computed in Lua on every backend (both share the constants/recurrence, so
    the result is identical either way). Returns nil on a non-match.

                                                        *lvim-fuzzy.backend()*
require("lvim-fuzzy").backend()  → "native-avx2" | "native-scalar" | "lua"

Other introspection: `native_loaded()`, `library_path()`, `abi()`,
`native_abi()` — used by |lvim-fuzzy-health|.

Example: >lua
    local fuzzy = require("lvim-fuzzy")
    local ctx = fuzzy.prepare({ "getClient", "config_set", "buffer.line" })
    local results = fuzzy.match("gc", ctx)
    for _, r in ipairs(results) do
        print(r.index, r.score)
    end
    -- grow the pool cheaply; the existing entries are not rebuilt
    fuzzy.append(ctx, { "getConfig", "get_client" })
<
                                                          *lvim-fuzzy-append*
Incremental append ~

For a growing pool (a picker streaming results, a completion source that keeps
discovering words), |lvim-fuzzy.append| extends a prepared context in place and
builds ONLY the new candidates' data — the existing pool's offsets, signatures
and lengths are never touched. So the cost is proportional to the number of NEW
candidates, not the pool size: appending 5,000 candidates is roughly constant
whether the pool holds 200,000 or 1,500,000, while a full re-prepare scales with
the total. Measured (native, AVX2):

    base pool     append(+5000)    full re-prepare    saving
    200,000       0.32 ms          7.3 ms             ~23x
    1,500,000     0.39 ms          51.8 ms            ~134x

The result of prepare(A) then append(B) is byte-identical (same indices, scores
and order) to prepare(A ++ B), on every backend — asserted by a Rust test
(`append_equals_prepare_whole`) and a headless native-vs-Lua-vs-whole cross
check. Incremental append needs the native backend at ABI >= 2; a pure-Lua
backend or an older library still returns identical results, falling back to a
full re-prepare on the next match.

4. BACKENDS & CORRECTNESS                                *lvim-fuzzy-backends*

Two backends, one ranking:

  native   the Rust cdylib. On an AVX2 x86_64 CPU the inter-candidate SIMD tile
           is active ("native-avx2"); otherwise a scalar path ("native-scalar").
           The SIMD and scalar paths are proven byte-identical by an in-crate
           test (`simd_matches_scalar`).
  lua      the pure-Lua matcher in `lua/lvim-fuzzy/fallback.lua`, a byte-exact
           mirror of the native scorer — same bonus constants, same affine-gap
           recurrence, same deterministic total order.

Because every path implements the identical model, a consumer sees the SAME
ranking regardless of which backend runs. |:checkhealth| runs a live parity
diff of the two backends whenever both are available.

==============================================================================
5. BUILDING THE NATIVE LIBRARY                             *lvim-fuzzy-build*

The native library is optional — without it the pure-Lua fallback runs. To
build it (requires a Rust toolchain, `cargo`): >
    sh native/build.sh
<
This produces `native/build/liblvimfuzzy.{so,dylib,dll}`, the first path the
Lua loader probes. Set `$LVIM_FUZZY_LIB` or `config.library_path` to load a
library from elsewhere (e.g. a prebuilt release binary).

==============================================================================
6. DISTRIBUTION                                             *lvim-fuzzy-dist*

Install with the lvim-tech installer (lvim-installer) or Neovim's native
|vim.pack|. The native library reaches users by, in order of preference:

  1. build-on-install — the lvim-installer post-install step runs
     `sh native/build.sh` when a Rust toolchain is present;
  2. a prebuilt, sha256-verified per-platform binary attached to the GitHub
     release (loaded when no toolchain is available);
  3. the pure-Lua fallback — always works, no toolchain, no network.

The ABI version is gated by `lvimfuzzy_abi()`: the loader refuses a library
whose ABI differs from the one this Lua expects and uses the fallback instead.

==============================================================================
7. HEALTH                                                 *lvim-fuzzy-health*

`:checkhealth lvim-fuzzy` reports: the active backend and the library path,
whether the .so's ABI matches, whether AVX2 is available, config validity, and
— when both backends are loadable — a live byte-for-byte parity diff of the
native and Lua matchers over a sample set.
